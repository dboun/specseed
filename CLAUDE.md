# CLAUDE.md

Invoke `./skills/specseed/references/caveman.md` skill.

This repo is the **source + installer for the `specseed` skill** (a Claude Code / Codex skill). It is NOT an application — there is nothing to "run". You are a dev of this skill: you edit the skill's instructions (markdown) and its tooling (python scripts).

Do not confuse this repo's files with the artifacts the skill *produces*: at runtime, in a TARGET repo, specseed writes a `.specseed/` tree (spec docs + a `project_management/` work breakdown). That tree does not exist here.

## Layout

```
skills/specseed/
  SKILL.md            # entry/router: modes, output hierarchy, protocols. START HERE.
  references/         # the actual behavior — loaded by SKILL.md as needed
    bootstrap.md      #   greenfield flow (stages 1–14)
    adapt.md          #   non-trivial changes to an existing spec
    tweak.md          #   single-doc edits (+ escalation rules)
    work-breakdown.md #   roadmap + epic/ticket/issue formation (the 3-tier model)
    component-questions.md, question-protocol.md   # questioning subroutines
    CLAUDE_template.md# the CLAUDE.md specseed writes into TARGET repos (impl-agent runtime)
    caveman.md        # doc-writing style (terse, signal-dense)
  scripts/            # stdlib-only python3 tooling (NO third-party deps)
install.sh            # copies skills/specseed → ~/.claude/skills and ~/.agents/skills
README.md
```

## Mental model (the work layer specseed builds)

Three tiers: **epic → ticket → issue**.
- epics + tickets = PM / non-technical. Tickets carry `satisfies_reqs` + the critical-path `depends_on` DAG.
- issues = technical, the unit an agent claims and executes.
- **Folders are source of truth**; `tickets.json` / `issues.json` are GENERATED by the assemble scripts and hold live runtime state (status/claim). Frontmatter is flat `key: value` with inline JSON for lists/objects (so the parsers stay stdlib-only).
- Critical path is at the **ticket** tier; issues are claimed at the **issue** tier.

## Scripts (in skills/specseed/scripts/)

`requirements_generate_json.py` (SRS tables→reqs.json), `requirements_analyze.py`*/`tickets_analyze.py`* (USER-PROVIDED analyzers), `issues_assemble.py` + `tickets_assemble.py` (folders→json; issues first, ticket effort/counts derive from issues), `issues_validate.py` + `tickets_validate.py` (kept separate by design), `claim_issue.py` (atomic flock claim; no-arg auto-picks next ready issue), `issue_info.py`, `roadmap_render.py` (bump ROADMAP "(X/Y)" counts), `verification_map.py` (req→ticket→issues→tests), `drift_check.py`.

## Conventions

- Scripts: python3, **stdlib only**. Keep it that way (no PyYAML etc).
- Test a script by building a tiny `.specseed/` fixture under `/tmp` and running the chain (issues_assemble → tickets_assemble → validators → claim_issue → verification_map). Clean up after.
- Skill doc-writing style: caveman-spirit — lean, fragments OK, no filler (see `references/caveman.md`). User-facing comms start normal then go terse.
