# Work breakdown subroutine (roadmap + epics + tickets + issues)

Used in bootstrap (roadmap stage + formation stage) and adapt mode when new
work is needed. Covers the three-tier work model and the ROADMAP.

## The three tiers

```
epic    →  ticket   →  issue
(PM)       (PM)        (technical)
```

- **Epic** — a large outcome / theme. Non-technical, PM-facing. Groups tickets.
- **Ticket** — a unit of user-visible value. Non-technical, PM-facing. May belong
  to an epic. Carries `satisfies_reqs` (the requirements it fulfills) and the
  critical-path `depends_on` DAG. Groups issues.
- **Issue** — a technical, executable unit of work. May belong to a ticket. The
  thing an agent CLAIMS and runs (carries `artifacts`, `effort_hours`, `plan.md`,
  `step_reports/`). INVEST applies HERE.

There is NO separate "story" tier — a user story is a `## Story` section inside a
ticket's prose body.

Each entity is a folder under `.specseed/project_management/<tier>s/<ID>/` with a
main `<ID>.md` file: YAML-ish **frontmatter** (machine fields) + markdown **prose**
body. The folders are the source of truth; `tickets.json` / `issues.json` are
GENERATED by the assemble scripts.

## Inputs

- `.specseed/spec/reqs.json` (settled reqs, generated from SRS)
- `.specseed/spec/sad.md` and `.specseed/spec/sdd.md` (or per-component variants)
- `.specseed/memory.md` (recent context — component summaries from stage 4)
- The approved `ROADMAP.md` (see "ROADMAP" below — drafted and approved BEFORE detailed formation)

## ID formats

- **Epic:** `EPIC-NNNN` (zero-padded). Global numbering.
- **Ticket:** `PROJ-NNNN` (zero-padded). Project-wide sequential, PM-facing.
- **Issue:** `<TYPE>-NNNN` typed: `FEAT-0001`, `BUG-0042`, `CHORE-0007`, `SPIKE-0003`.

## Frontmatter format

Flat `key: value`, one per line. Structured values (lists/objects) use **inline
JSON**. Bare unquoted strings are allowed for scalars. The assemble scripts parse
each value as JSON, falling back to a bare string.

### Epic — `epics/<EPIC-NNNN>/<EPIC-NNNN>.md`

```yaml
---
id: EPIC-0001
title: Account security
status: todo            # todo | in_progress | done | deprecated
tickets: ["PROJ-0042", "PROJ-0043"]
---
## Goal
<the outcome, non-technical — what's true for users when this epic is done>
## Why
<why this matters now>
## Success signals
<observable signals the epic landed>
```

### Ticket — `tickets/<PROJ-NNNN>/<PROJ-NNNN>.md`

```yaml
---
id: PROJ-0042
title: Add password reset flow
epic: EPIC-0001          # or null
type: feature            # feature | bug | chore | spike
priority: high           # high | medium | low
status: todo             # todo | in_progress | blocked | done | deprecated
depends_on: ["PROJ-0040"]   # OTHER TICKET ids — this is the critical-path DAG
satisfies_reqs: ["SRS-API-012", "SRS-API-013"]
issues: ["FEAT-0101", "FEAT-0102"]
---
## Story
As a user who forgot my password, I want to reset it via email so I regain access.
## Description
1–3 sentences: what + why (the PM framing).
## Acceptance criteria        (PRODUCT-level — what proves the value shipped)
- User can request reset from the login page
- Email arrives within 60s
- Link expires after 24h
- Works on mobile
```

`effort_hours`, `issues_total`, `issues_done` are NOT authored — `tickets_assemble.py`
derives them (effort = sum of child issues; counts feed ROADMAP "(X/Y)").

### Issue — `issues/<FEAT-NNNN>/<FEAT-NNNN>.md` (+ `plan.md`, `step_reports/`)

```yaml
---
id: FEAT-0101
title: Reset-request endpoint
ticket: PROJ-0042        # or null
type: feature            # feature | bug | chore | spike
component: api
effort_hours: 0.5        # AGENT-TIME estimate (see below)
depends_on: []           # OPTIONAL intra-ticket issue ids (local ordering only)
status: todo             # todo | in_progress | blocked | done | deprecated
claimed_at: null
claimed_by: null
artifacts: {"touches": ["src/api/auth/"], "tests": ["tests/api/test_reset.py"], "migrations": []}
notes: ""
---
## Acceptance criteria        (TECHNICAL — what proves THIS issue done)
- POST /auth/reset-request returns 202
- Unknown email still returns 202 (no account enumeration)
## Notes
<implementation notes, gotchas>
```

### Field semantics

- `type`: `feature` / `bug` / `chore` / `spike`
- ticket `depends_on`: other TICKET ids blocking this ticket — the analyzed DAG
- issue `depends_on`: other ISSUE ids for local ordering within/near a ticket (NOT the critical path)
- ticket `satisfies_reqs`: 1–8 req IDs this ticket proves (issues inherit via parent)
- `status`: `todo` / `in_progress` / `blocked` / `done` / `deprecated`
- `claimed_at` / `claimed_by` (issues only): set by `claim_issue.py` when status → `in_progress`; `null` otherwise
- `artifacts.touches` / `.tests` / `.migrations` (issues only): dirs/files, test paths, forward-migration paths
- `effort_hours` (issues only): **estimated agent time** to complete the issue (e.g. ~0.5h for a medium issue), NOT human days. Critical-path effort per ticket is the sum of its issues'.

## INVEST (applies to ISSUES)

Each issue should be:
- **I**ndependent — minimal coupling to other issues
- **N**egotiable — scope can shift in conversation
- **V**aluable — advances its ticket's value, or reduces risk (a spike)
- **E**stimable — you can guess agent-time
- **S**mall — one focused agent session
- **T**estable — has technical acceptance criteria with clear pass/fail

## Acceptance criteria ≠ requirements

- **Requirements** (`srs.md`, IDs `SRS-...`): what the *system* does. Persistent.
- **Ticket acceptance criteria**: PRODUCT-level — what proves *this ticket's value* shipped.
- **Issue acceptance criteria**: TECHNICAL — what proves *this issue* done.

A ticket may satisfy 1–8 reqs. Don't force criterion-to-req 1:1 — criteria
demonstrate *the work landed*; reqs describe *what the system does*.

## Sizing heuristics (concrete) — applied at the ISSUE level

Two checks, apply both:

**Check 1 (semantic):** if you can name 2–6 technical acceptance criteria with
confidence, the issue is right-sized.
- `<2` → too small/trivial; merge with a related issue
- `>6` → too big; split into vertical slices

**Check 2 (mechanical):** estimated `effort_hours` fits one focused agent session.
- too big → split, even if check 1 passes

Apply check 1 first; if it passes but check 2 fails, split anyway.

## Vertical slice heuristic

Cut issues so each produces **observable behavior change in one run/request**. If
you can describe what the user (or upstream system) sees differently after the
issue ships in one sentence, it's a valid slice. Slices may skip layers; the rule
is observability, not "touches every layer".

## Integration issues

Insert an integration issue **before any merge point where ≥2 parallel branches
converge** (an issue whose `depends_on` lists 2+ issues from different parallel
branches). Err toward inserting if branches span ≥2 components or ≥4 issues each.

## Formation technique

1. **Start from the approved ROADMAP** — epics + ticket titles are already agreed.
2. **Flesh each ticket**: write the story, description, product acceptance criteria;
   set `satisfies_reqs` (topo-sorted by req `depends_on`); set ticket `depends_on`
   (the critical-path DAG).
3. **Decompose each ticket into issues** — vertical slices, INVEST, sizing checks.
4. **Set issue artifacts** (`touches`, `tests`, `migrations`) and `effort_hours`.
5. **Insert integration issues** at parallel merge points.
6. **Back-link**: each ticket's `issues:` list ⟷ each issue's `ticket:` parent.
7. **1–8 reqs per ticket.** More → split the ticket.

## Critical path (TICKET tier)

After folders are written, assemble then analyze:

```bash
python .specseed/scripts/issues_assemble.py
python .specseed/scripts/tickets_assemble.py     # derives per-ticket effort from issues
python .specseed/scripts/tickets_analyze.py .specseed/project_management/tickets.json
```

`tickets_analyze.py` returns the critical path = longest dep chain (by summed
effort). Determines minimum project duration.

- Schedule critical-path tickets first; their issues get the best agent / highest priority.
- Parallel branches run alongside. **"Important" ≠ "on critical path".**
- Re-run after status changes — a slipping parallel branch can become critical.

Surface critical path to user. If unreasonably long, it often signals overly
narrow tickets or artificial dependencies — rebalance.

## Migrations

Issues that change **data shape** (DB schema, persisted file format, on-disk
state, config schema) need migration handling:

1. **`artifacts.migrations`** — list forward-migration script paths. `issues_validate.py` checks existence (warning).
2. **Acceptance criterion**: include one phrased "migration script committed at `<path>` and runs cleanly against current schema".

Optional: document rollback in `notes`; note deployment ordering in `notes`.

For retired features (see `adapt.md`), cleanup migrations get their own
`CHORE-NNNN` issues with the same treatment.

## Spike post-completion

Spike issues (`type: "spike"`) are time-boxed research. **Before marking a spike
`done`, the implementation agent MUST capture findings** in the issue's `notes`
(or body), else the learning vanishes:

```
Spike report:
- Question: <what was investigated>
- Investigation: <what was tried — sources, prototypes, benchmarks (1-2 lines)>
- Findings: <what was learned (1-3 lines)>
- Decision: <chosen path, or "no decision yet — see Followups">
- Followups: <ADR row? new req? SDD update? → tell user to use /specseed>
```

Then: decision made → `/specseed` to add an ADR row; new/changed reqs → `/specseed
adapt`; SDD pattern surfaced → `/specseed adapt`. Only THEN mark `done`. Do not
auto-invoke adapt from spike completion — surface to user with a recommendation.

## Grouping & sequencing

Project grouping/sequencing lives in `ROADMAP.md` **phases** (see "ROADMAP"
below). There is no `milestone` field on tickets. Finer-grained scheduling
(sprints) may be added later.

## The art part (judgment calls)

- **Where to cut vertical slices spanning 2 components** — pick the slice with the smaller cross-component contract; tie → the component the team knows better.
- **When to merge tightly-coupled issues** — identical scope + one depends only on the other → consider merging.
- **When to defer a spike** — off critical path → defer; on it → schedule immediately.

When unsure, surface to user with a 1-line trade-off summary; don't ask open-ended.

## Validation

After writing/editing folders, ALWAYS assemble then validate BOTH tiers:

```bash
python .specseed/scripts/issues_assemble.py
python .specseed/scripts/tickets_assemble.py
python .specseed/scripts/issues_validate.py
python .specseed/scripts/tickets_validate.py
```

`issues_validate.py`: schema, enums, positive `effort_hours`, `depends_on` refs +
cycles, parent `ticket` ref, artifacts shape, test/migration existence (warnings),
claim invariants. `tickets_validate.py`: schema, enums, `depends_on` refs + cycles,
`satisfies_reqs` ref into `reqs.json`, `epic` ref, `issues` refs + back-consistency.

Fix any errors before critical-path analysis.

## ROADMAP

`.specseed/project_management/ROADMAP.md` is the PM-level map, **drafted and
approved with the user BEFORE detailed ticket/issue formation** (bootstrap roadmap
stage; see `bootstrap.md`).

Structure:
- **Phases** (`## Phase 1 — <name>`) — NOT necessarily quarters; logical stages.
- **Subsections** under a phase (`### <area>`) — at least one carries a list of
  epics, each with a sub-list of its tickets (titles).
- Each ticket title is annotated `(X/Y complete)` = issues done / total issues
  for that ticket (sourced from `tickets.json` `issues_done`/`issues_total`).

```markdown
# Roadmap

## Phase 1 — Foundations
### Accounts
- **EPIC-0001 Account security**
  - PROJ-0042 Add password reset flow (0/2 complete)
  - PROJ-0043 Add 2FA (0/3 complete)

## Phase 2 — Growth
### Billing
- **EPIC-0002 Subscriptions**
  - PROJ-0050 Stripe checkout (0/4 complete)
```

The `(X/Y complete)` counts are bumped in-place by `roadmap_render.py` from
`tickets.json` (`issues_done`/`issues_total`). It runs in the issue finish flow
(after `tickets_assemble.py`) and the adapt/tweak cascades, so counts track
completion as issues land. `roadmap_render.py --check` reports drift without
writing. Counts are display-only — nothing depends on them.

### Roadmap discussion gate

Before fleshing tickets/issues, present the draft ROADMAP — phases, epics, ticket
TITLES, and short comments — and discuss with the user. Adjust phases/epics/ticket
groupings per feedback. Only after approval proceed to detailed formation above.
