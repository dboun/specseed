# Migrate to 0.2.0

## What changed (and why this is breaking)

0.2.0 is a ground-up rebuild. There is nothing in a 0.1.0 tree that maps field-for-field onto 0.2.0, so there is **no mechanical transform** — this hop re-derives the spec into the new format.

- 0.1.0 produced a **repo-root `spec/`** tree (`vision.md`, `srs.md`, `sad.md`, `sdd.md`, `reqs.json`, flat `tickets/`) + a small flat `scripts/` set, and a `docs/` (e.g. `docs/CONTRIBUTE.md`). NO `.specseed/`.
- 0.2.0 produces a **`.specseed/`** tree: `spec/` + a 3-tier `project_management/` work breakdown (epics/tickets/issues/sprints), `memory/config.json`, `version.txt`, the `scripts/core` + `scripts/remote` tooling, and the runner. Different frontmatter, different JSON schemas, different folder layout.

So the old `spec/` can't be edited into shape. It becomes an **import source** for a fresh **adopt** (reverse-bootstrap), exactly as adopt treats any pre-existing docs. Originals are left frozen; the new `.specseed/` becomes source of truth.

## Detect (when this hop applies)

This hop runs only for a genuine 0.1.0 tree. Confirm BEFORE doing anything:
- **No `.specseed/`** in the repo (if one exists, this is not a 0.1.0 tree — stop, use the normal migrate path).
- Old 0.1.0 markers present at the repo root: `spec/srs.md`, `spec/sad.md`, `spec/sdd.md`, `spec/vision.md` (any subset is enough to recognize it), and commonly `docs/CONTRIBUTE.md`.

## Steps

1. **Signal the version jump.** Tell the user plainly: their spec was built by specseed **0.1.0**; **0.2.0** is a different, much larger format (work breakdown + runner + config), so there is no in-place upgrade. You will **re-adopt** their existing docs into the new `.specseed/` tree, leaving the old `spec/` and `docs/` untouched as frozen reference.
2. **Quick confirm.** One gate — "re-adopt from your existing `spec/` + `docs/` into the new `.specseed/` format? (recommended)". Let them veto/defer. Do not drag it out.
3. **Configure.** Run **configure mode** (`routes/configure.md`) — hand off to `scripts/configure.py`, then provision. This writes `.specseed/memory/config.json` and the new `scripts/` tree, and stamps `.specseed/version.txt` = `0.2.0`. (This is what "any scripts etc. get replaced" means — the new tooling lands here; the old flat 0.1.0 `scripts/` are obsolete and simply unused.)
4. **Adopt.** Run **adopt mode** (`routes/adopt.md`) with the old docs as the import inventory (stage 2): `spec/vision.md`→vision, `spec/srs.md`→SRS, `spec/sad.md`→SAD, `spec/sdd.md`→SDD, and `docs/CONTRIBUTE.md` → agent-rules / project-conventions reconciliation (stage 3). Code stays ground truth; reconcile per adopt stage 6. NEVER edit the old `spec/`/`docs/` in place (adopt invariant 3) — propagate-back is the opt-in offer at adopt stage 9.
   - `# REVIEW:` adopt re-derives the spec from code + old docs; it is not a 1:1 copy. The recovered `.specseed/spec/` may differ from the 0.1.0 `spec/` where the code disagreed with the stale doc. The user reviews the recovered spec in adopt's normal review pass.

This hop's terminal action is **entering adopt** — it does not return to migrate's generic step loop. Once adopt finishes, the tree is already the new format and already stamped `0.2.0`.

## Verify

- `.specseed/` exists with `spec/` content + `project_management/` + `memory/config.json`.
- `cat .specseed/version.txt` → `0.2.0`.
- `python3 .specseed/scripts/core/config.py validate` exits 0 (config schema OK).
- Old repo-root `spec/` and `docs/` are unchanged (frozen reference), unless the user opted into propagate-back at adopt stage 9.
